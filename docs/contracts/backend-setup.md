# Contract: Backend First-Launch Setup — **[Implemented]**

Backend: `backend-sonic` branch `feat/setup-mode-health`, storage modes added
on `feat/local-storage`. The mobile app only consumes these endpoints; it
never installs, configures, or starts the backend beyond submitting the
wizard's configuration patch. The database URL is entered only in the
Termux installer — the app never collects or sends it, and the wizard never
opens while the database is unconfigured.

Implementation: `src/features/server/api/setupApi.ts`
(`getSetupStatus()`, `saveSetupConfig()`, `pollHealthUntilReady()`),
`src/features/server/hooks/useSetupWizard.ts`,
`src/features/server/screens/SetupWizardScreen.tsx` +
`src/features/server/components/Setup*Step.tsx`, route
`src/app/(auth)/setup-wizard.tsx`.

## `GET /setup/status` — **[Implemented]**

- Auth: `X-Setup-Token: <token>` header. No user access/refresh token is
  ever sent; plain `fetch` bypasses the apiClient interceptors.
- Response: `{ setupRequired: boolean, configured: Record<string, boolean>,
  envLocked: string[], storageModes?: ("local" | "r2")[] }`. `configured`
  flags which config keys already have values (including `STORAGE_MODE` on
  new backends); `envLocked` lists keys managed by the backend environment
  that must never be submitted. `storageModes` advertises the configurable
  modes; older backends omit it, which reads as R2-only with no mode
  submitted (see below).
- Errors: 401/403 → invalid token (user must re-check the Termux output);
  network/timeout → retryable; any other shape → unexpected.
- The setup token is generated by the backend at first startup, printed to
  the Termux console as `SETUP TOKEN: ...`, and stored hashed server-side.
  It is never returned by this endpoint. The app keeps it in wizard memory
  only: never logged, never persisted, never echoed in error messages.
  There is no token-recovery endpoint; the UI says the token is shown once.

## `POST /setup/config` — **[Implemented]**

- Auth: `X-Setup-Token` header, same rules as above.
- Body: a flat JSON object of string values using only these keys —
  `STORAGE_MODE` (new backends only, `"local"` or `"r2"`),
  `R2_ACCOUNT_ID`, `R2_ACCESS_KEY`, `R2_SECRET_KEY`, `R2_BUCKET`,
  `WORKER_STREAM_URL`, `JWT_PLAYBACK_SECRET`, `YOUTUBE_API_KEY`,
  `LASTFM_API_KEY`. Unknown keys, locked keys, non-string values, and empty
  patches are rejected. The wizard sends every entered value in ONE request
  on Finish and never sends blanks or environment-locked keys. Values go out
  verbatim apart from trimming surrounding whitespace, so the playback
  secret matches the Cloudflare worker exactly.
  - R2 mode sends the R2 + playback + API-key values as before, plus
    `STORAGE_MODE: "r2"` only when the backend advertised modes. Older
    backends get the byte-identical pre-existing patch (no `STORAGE_MODE`).
  - Local mode sends `STORAGE_MODE: "local"` plus the YouTube/Last.fm keys
    only — never R2 credentials, `WORKER_STREAM_URL`, or
    `JWT_PLAYBACK_SECRET` (the backend generates and persists the playback
    secret on a local save).
- Success: `{ saved: true, setupRequired: boolean, migration?: { status,
  steps: string[] }, restartRequired?: boolean, storageMode?: "local" | "r2",
  generatedKeys?: string[] }`. `generatedKeys` names (never values) secrets
  the backend generated, e.g. the local-mode playback secret. The API exits
  after responding so the supervisor can restart it — a save success is NOT
  proof the API is ready (see the poll below).
- Failure: 401 → bad setup token; 400 carries a `message` that is shown to
  the user. Backend messages are redacted against submitted secrets before
  display (`redactSecrets()`), since an echo could otherwise unmask a value
  the UI keeps hidden.

## Readiness: poll public `GET /health` — **[Implemented]**

- After the save (or immediately, when nothing needed sending), the app
  polls `GET /health` (plain fetch, no auth headers) every 2s for up to
  120s. Every failed attempt — refused connection during the API restart,
  timeout, unparsable body — is tolerated; only the deadline ends the poll.
- Ready means `setupRequired === false` AND `db === 'ok'` (same
  `parseHealthPayload()` the validator uses). Without an expected mode (older
  backends, environment-owned mode), `features.storage` never blocks
  completion. When the wizard submitted a mode, readiness additionally
  requires `features.storage` to equal it, so a save that did not take
  effect cannot finish silently. Only then does the wizard finish.
- Worker health (port 3001) is separate and not required for completion.

## Wizard flow (client-side)

1. The setup screen validates the URL via `/health` — every Continue
   re-validates, including an unchanged URL. `setupRequired: true` with a
   healthy database persists the URL through the existing server
   store/switch paths (URL + setup flag + request id in one atomic
   `setServer()` commit); ServerGuard then pushes `/setup-wizard`, so the
   wizard opens even if the setup screen unmounts. A saved server is also
   re-checked in the background on boot (non-blocking): setup discovery
   commits the same pending flag via `markSetupPending()`, which keeps the
   session and routes exactly once, even for a signed-in user. `db: down`
   and `db: unconfigured` show retryable errors and never open the wizard.
2. Step 1 collects the setup token and validates it via `/setup/status`,
   concurrently reading the current mode from public `/health` (fail-open).
3. Step 2 offers the storage mode (Local / Cloudflare R2 cards) — only when
   the backend advertised more than one mode and the environment does not own
   `STORAGE_MODE`; older backends keep the R2-only step unchanged. The choice
   preselects the server's current mode so an already-configured server is
   never silently switched; picking another mode warns that existing songs
   are not migrated. R2 then collects the four R2 keys (access key and secret
   key masked); Local collects nothing (no R2, worker, or playback-secret
   fields exist) and skips step 3.
   Step 3 (R2 only) collects `WORKER_STREAM_URL` (must be a valid http(s)
   URL) and `JWT_PLAYBACK_SECRET` (masked; must match the Cloudflare
   worker).
   Step 4 collects `YOUTUBE_API_KEY` and `LASTFM_API_KEY` (both masked) in
   both modes.
   Every field is required unless already configured (blank keeps the saved
   value) or environment-locked (shown as managed). Steps validate locally
   and save nothing; entered values survive back-navigation and retries.
4. Step 5 (Finish) sends all entered values in one `POST /setup/config`,
   then polls to readiness. A save failure keeps the values for editing; a
   poll timeout retries the poll only, unless values changed since the save
   — edits made after a successful save are sent again.
5. Completion validates the kept session against the restarted backend:
   home when it is still valid, login otherwise.
